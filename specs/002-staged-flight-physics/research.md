# Research: Полёт 2.0 (Phase 0)

**Date**: 2026-09-06. Решения приняты по исходникам проекта, деобфусцированному jar Minecraft 26.2 (`javap`) и стандартным моделям баллистики; неизвестных из Technical Context не осталось.

## R6. Ступени: плоскости против компонент связности

- **Decision**: ступень задаётся горизонтальной плоскостью разделителя (всё на уровне разделителя и ниже — нижняя ступень). Ступени упорядочены по Y разделителей снизу вверх.
- **Rationale**: тот же принцип, что у стыковочного узла (`DockingSystem.clampLocalY`) — игроку понятно и однозначно; компоненты связности после удаления разделителей дают неоднозначный порядок зажигания для боковых ускорителей (одинаковый minY) и требуют отдельного UI для расписания ступеней (как в KSP).
- **Alternatives considered**: компоненты связности + расписание ступеней (полный KSP) — отложено в бэклог «радиальные ускорители»; ручная нумерация ступеней предметом — лишняя сущность.

## R7. Интегратор: активный вид структуры вместо второго интегратора

- **Decision**: не менять `FlightIntegrator.step`; `StageLayout.activeView` превращает двигатели и баки неактивных верхних ступеней в корпус с массой, а нижние ступени убирает. Пул топлива состояния = топливо активной ступени.
- **Rationale**: `withTotalPropellant` перераспределяет пул только по деталям с ёмкостью > 0 — у «замороженных» баков ёмкость 0, и их топливо остаётся фиксированной массой; `PerformanceCalculator` на активном виде автоматически даёт TWR и Δv ступени с верхними как грузом. Ноль изменений в проверенной математике интегратора, тесты 001 остаются валидными.
- **Alternatives considered**: маска активных двигателей в `ControlInput` и раздельные пулы в `FlightState` — ломает сигнатуры и все существующие тесты; per-tank топливо в `RocketData.Entry` — правильнее, но шире scope (стыковка, разборка, сборка), отложено.

## R8. Ввод ориентации: штатный `Input` и `getYHeadRot`

- **Decision**: команды наклона читаются из `ServerPlayer.getLastClientInput()` (`forward/backward/left/right`, `javap` подтверждает поля записи `Input` в 26.2), направление — от `Entity.getYHeadRot()`; отделение ступени — отдельная клавиша + C2S-пакет через существующий `ModNetworking`.
- **Rationale**: пакет ввода уже питает тягу и выбор цели (T054), клиент шлёт его при изменении — новых клиентских пакетов для наклона не нужно (принцип VI). Отделение — необратимое действие, ему нужна осознанная клавиша (по умолчанию X, не занята ванилью), а не удержание Ctrl.
- **Alternatives considered**: `shift` — в ванили дисмаунт с транспорта; спринт в полёте — легко нажать случайно.

## R9. Атмосфера: экспоненциальный профиль в игровом масштабе

- **Decision**: `ρ(y) = ρ₀·exp(−(y−datum)/H)`, поля `atmosphere_density`, `scale_height`, `datum_y` в профиле тела; Земля 1.225/110/63, Марс 0.020/150/64. Отсутствие плотности — вакуум.
- **Rationale**: реальная высота шкалы (8.5 км) не имеет смысла при высоте перехода 450 м — атмосфера была бы одинаково плотной на всём подъёме. H = 110 даёт ~3% плотности у перехода: сопротивление важно у земли и исчезает к орбите, как в реальности по форме кривой. Марс: реальная плотность у поверхности 0.020 кг/м³ — в 60 раз тоньше, лом и ракета это чувствуют.
- **Alternatives considered**: линейный профиль до высоты перехода — не физичен; таблица по высотам — избыточна для датапака.

## R10. Модель сопротивления: квадратичная с проекцией коробки

- **Decision**: `F = −½ρ|v|C_dA_eff·v̂`, `A_eff = A_x|v̂_x| + A_y|v̂_y| + A_z|v̂_z|` (площади проекций AABB структуры), C_d из конфига (0.5 ракета, 0.1 лом, 1.0 метеорит). Линейное `dragCoeff` в `ProjectileSpec` заменяется.
- **Rationale**: единая модель для ракет, ломов и метеоритов; проекция коробки — честная оценка площади для блочных структур без расчёта формы; C_d = 0.5 — среднее между конусом (0.3) и кубом (1.05), документируется как упрощение. Числа: лом 2 т/1500 м/с у поверхности Земли теряет ~2 м/с² — проценты; ракета 3.2 т с A = 1 м²: терминальная ~320 м/с; капсула 250 кг: ~90 м/с.
- **Alternatives considered**: коэффициент по форме структуры (отношение высоты к ширине) — отложено; оставить линейную модель — не физика.

## R11. Нагрев: Саттон-Грейвс без радиуса затупления

- **Decision**: индекс `q = √ρ·v³`; урон экипажу при `q > threshold` (6·10⁶) без возвратной капсулы в стеке; напор `½ρv²` — информационно в скане с предупреждением при > 35 кПа.
- **Rationale**: закон Саттона-Грейвса `q̇ = k√(ρ/R_n)·v³` — стандарт входа; коэффициент и радиус затупления сворачиваются в порог конфига. 6·10⁶ ⇒ ~176 м/с у поверхности Земли: штатный подъём (~100–120 м/с к 450 м) не греет, вход с −150 м/с у земли (после падения без тормозного импульса с 430 м набирается ~85 м/с) — тоже нет, а вот отвесное падение с орбитального перехода без ретро-импульса на тяжёлом стеке или разгон у земли — греют. Порог легко подстроить в конфиге.
- **Alternatives considered**: разрушение конструкции от напора — отложено (ещё один способ умереть без нового смысла); нагрев по кинетической энергии — не отличает плотную атмосферу от тонкой.

## R12. Симулятор подъёма как замена `1.15·√(2gh)`

- **Decision**: `AscentSimulator` — тот же полу-неявный Эйлер (dt 0.05) вертикально на полной тяге с авто-отделением и сопротивлением; результат — достигнута ли высота перехода, Δv до неё, пиковый напор, время.
- **Rationale**: одна и та же математика для прогноза и полёта — вердикт «годен» совпадает с реальностью на вертикальном подъёме; стоимость подъёма честно включает гравитационные и аэродинамические потери. 450 м при dt 0.05 — ~300 шагов на ступень, микросекунды.
- **Alternatives considered**: аналитика с поправками — не учитывает многоступенчатость и сопротивление; сохранить √(2gh) — обман скан-отчёта.

## R13. Точность удара: равномерный круг вместо нормального распределения

- **Decision**: смещение равномерно по площади круга радиуса R (`r = R√u`), R = 0.5 (наводимый) / 10 (ненаводимый) блоков из конфига; режим — по `SpaceNetworkState.hasCoverage(целевое измерение)`; фиксируется при выстреле.
- **Rationale**: «разброс до N блоков» понятен игроку и проверяем стендом (100% в круге); нормальное распределение с КВО требует объяснять хвосты. Покрытие по измерению — уже существующая семантика спутников (Phase 13), спутник получает вторую роль.
- **Alternatives considered**: косой вход с горизонтальной составляющей — потребовал бы удерживать коридор чанков в сотни блоков (десятки радиус-1 билетов на выстрел, генерация чанков) — нарушает бюджет производительности; отвергнуто с обоснованием в спеке.

## R14. Тест-хуки стенда

- **Decision**: стенд управляет ракетой серверными методами (`RocketEntity.ignite`, `launchUnmanned`, `requestStageSeparation`, `setFlightVelocity`, аксессоры ступеней), как уже делает с `DockingSystem`/`RocketInteractions`; клавиши через `TestInput` не используются.
- **Rationale**: клиент шлёт `Input` только при изменении состояния клавиш — удержание через `TestInput.holdKey` конкурирует с реальным вводом клиента и ненадёжно под Xvfb; серверные хуки детерминированы и проверяют ту же серверную валидацию, что и пакет.
- **Alternatives considered**: `TestInput.holdKeyFor(Options::keyJump, n)` — оставлено как ручной сценарий в quickstart.

## R15. API 26.2, подтверждённое javap для этой фичи

- `net.minecraft.world.entity.player.Input` — запись `(forward, backward, left, right, jump, shift, sprint)`; `ServerPlayer.getLastClientInput()/setLastClientInput(Input)`.
- `Entity.getYHeadRot()`, `Entity.hurtServer(ServerLevel, DamageSource, float)` (у `LivingEntity` — публичная реализация), `Entity.push(Vec3)` + `hurtMarked`.
- `net.fabricmc.fabric.api.client.gametest.v1.TestInput` — `holdKey/pressKey/holdKeyFor/lookAt` (для ручных/будущих сценариев).
- Регистрация клавиши: `KeyMappingHelper.registerKeyMapping(new KeyMapping(name, Type.KEYSYM, GLFW key, KeyMapping.Category.GAMEPLAY))` + `ClientTickEvents.END_CLIENT_TICK` с `consumeClick()` — уже применяется для карты (M).
- Тип урона: JSON `data/spacereloaded/damage_type/<name>.json` + `new DamageSource(registry.getOrThrow(KEY))` — как `exposure`.
